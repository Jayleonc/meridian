# Meridian 项目治理

## 概览

这个 skill 用于所有会改变 Meridian 代码、架构、路线图、文档或执行优先级的工作。目标是让每次推进都有清晰归属：要么对应已有路线图，要么补充新的路线图/决策/待办，而不是只靠对话上下文临时推进。

## 总规则

非平凡 Meridian 变更不能直接进入实现。动手前要先把请求锚定到当前项目状态，再选择一个边界清晰、可验证的小切片。

很小的修复可以轻量处理，比如拼写、导入、单行配置；但只要影响运行方式、架构边界或项目方向，就必须同步相关项目记录。

Meridian 的项目级 skills 可以自我进化，但必须受控：只有当一次真实工作暴露出流程缺口、边界遗漏、验证盲区或重复人工步骤时，才更新 skill。不要为了“完善文档”而空泛扩写 skill。

## 必读上下文

开始 Meridian 任务时，只读取必要上下文：

- `README.md`
- `docs/ROADMAP.md`
- `docs/DECISIONS.md`
- `docs/ARCHITECTURE.md`
- 相关 `docs/specs/*-spec.md`
- 相关模块代码

优先使用 `rg` 和定向读取。不要一次性读取所有文档。

## 工作流程

### 1. 判断请求类型

根据用户请求判断类型，必要时向用户简短说明：

- **路线图执行**：实现已有路线图条目。
- **路线图修订**：新增能力或调整优先级。
- **架构决策**：改变组件边界、运行时模型、数据归属、供应商策略或 provider 体系。
- **战术修复**：修复局部问题，不改变项目方向。
- **探索咨询**：先解释、调查或比较方案，不直接实现。

如果请求无法映射到当前路线图，需要在实现前或同一变更中补充路线图条目。

### 2. 定义小切片

实现前要明确：

- 归属组件：Nexus、Atlas、Probe、Lens、Console、Trace、Codex 或 docs
- 用户能观察到的结果
- 预计修改的文件或模块范围
- 能证明有效的验证命令或手动检查

优先完成一个有用的纵向切片，不做大而散的半成品重构。

### 3. 检查架构边界

Meridian 默认边界如下：

- Console 通过 Nexus 访问后端；本地 Vite 代理也应指向 Nexus。
- Nexus 是唯一外部入口，开发服务器只暴露 `3000`。
- Atlas 是环境索引层：服务发现、运行时元数据、数据库 schema、语义标注。
- Probe 是日志证据层。
- Lens 是只读业务数据查询层，通过 DSL 控制查询边界。
- Agent runtime 负责会话、模型 provider 适配、工具编排。
- DevOps MCP 是开发者观察面：通过 Nexus 暴露只读运行状态、日志、配置和 smoke test；默认不得混入面向用户的 Agent Chat 工具面。
- 模型供应商必须藏在适配器后面，不能把 Meridian 绑定到单一供应商 SDK。
- Supervisor、Docker、Kubernetes 等运行时来源都应作为 Atlas discovery provider，不应写死。

如果用户请求会破坏这些边界，要指出风险，并选择保持边界清晰的实现路径。

### 4. 实现

按小切片实现，保持修改范围克制。不要借机做无关重构。

涉及 Agent 或工具行为时，优先顺序是：

- API / 数据模型契约
- provider / tool / runtime 边界
- UI 或 CLI 入口
- 文档、路线图、决策记录
- 验证

### 5. 更新项目记录

非平凡变更完成后，更新最小必要记录：

- `docs/ROADMAP.md`：进度、新计划、优先级变化
- `docs/DECISIONS.md`：架构承诺、边界决策、供应商策略
- `docs/ARCHITECTURE.md`：组件职责、核心流程变化
- `README.md`：命令、端口、环境变量、使用方式
- 相关 `docs/specs/*-spec.md`：只有规格本身变化时才更新

不要随便新建没人维护的计划文档。优先更新现有路线图和决策记录。

### 6. 验证并汇报

验证强度按影响范围决定：

- Python 后端：`python -m py_compile ...`、导入检查、端点 smoke test
- Console：`npm run build`
- Docker / 端口 / 配置：`docker compose config`、定向 `curl`
- Agent：配置端点、创建会话、必要时做一次小模型工具调用测试

最终回复应包含：

- 改了什么
- 更新了哪些路线图/决策/文档
- 跑了哪些验证
- 还剩什么缺口或下一个推荐切片

### 7. Hermes 自我进化

Hermes 是 Meridian 的项目级 skill 自我进化机制。它的目标是让治理规则从真实执行中学习，而不是停留在一次性写死的流程文档。

每次完成 Meridian 任务后，快速判断是否触发 Hermes：

- 本次工作是否暴露了 skill 没覆盖的项目边界？
- 是否出现了重复两次以上的人工判断或命令序列？
- 是否有新的组件职责、provider 策略、验证方式需要固化？
- 是否有用户明确指出“你这样推进不受控 / 不稳定 / 容易漂移”？
- 是否有旧规则误导了实现方向？

如果命中以上任一项，执行受控进化：

1. 用一句话描述触发原因。
2. 修改最小必要的项目级 skill 内容。
3. 如涉及架构承诺，同步 `docs/DECISIONS.md`。
4. 如涉及推进顺序，同步 `docs/ROADMAP.md`。
5. 运行 skill 校验。
6. 在最终回复中说明 skill 进化点。

禁止事项：

- 不要在没有真实触发事件时主动扩写 skill。
- 不要把临时偏好写成长期规则。
- 不要在 skill 中复制大段项目文档；只记录治理流程和关键边界。
- 不要把用户级 skill 当作 Meridian 权威规则；项目级 `.codex/skills/*` 才是权威。

## 路线图纪律

当用户提出新方向：

1. 判断它是否已经在 `docs/ROADMAP.md`。
2. 如果不在，先添加简洁路线图条目，或在本次实现中同步添加。
3. 如果改变核心边界，添加决策记录。
4. 每次选择足够小、能在当前回合完成并验证的切片。

## 示例

用户：“Atlas 以后要支持 Kubernetes 和 Docker 吗？”

处理方式：按架构决策处理。先确认 Atlas 是环境索引层；如果要实现，优先补 provider 抽象和路线图/决策记录，不把 Docker/Kubernetes 写死到上层 API。

用户：“继续做 Agent，可以直接做吗？”

处理方式：映射到智能诊断路线图，检查当前 Agent runtime，选择一个纵向切片，例如 streaming 或 Atlas 工具接入；实现后验证并更新路线图。

用户：“日志刷屏了，处理一下。”

处理方式：按战术修复处理。定位日志来源，窄范围修复，验证启动或配置；如果影响运行命令，则更新 README。

用户：“这个流程有点飘，需要稳定管理。”

处理方式：触发 Hermes。将暴露出的治理缺口沉淀到项目级 skill，必要时补充决策记录，并运行 skill 校验。
